## 5. MTP 收益结论

### 5.1 核心结论

**MTP n=1 投机解码在真实高熵任务（前端动画绘制）上未带来 decode 加速，反而略慢。**

| 维度 | 结论 | 数据支撑 |
|------|------|---------|
| Decode 加速 | ❌ 未加速，反而慢 | 全时段均值比 0.832（慢 16.8%）；B11 窗口均值比 0.742（慢 26%） |
| Prefill 保持 | ✅ 基本保持 | 全时段中位数比 1.003（几乎一致）；均值比 1.111（快 11.1%，但受离群值影响） |
| 任务完成度 | ❌ B 侧失败 | B10 崩溃 + B11 结尾死循环 |

### 5.2 与低熵基准对比

此前低熵基准测试（短上下文、低熵输入）显示 MTP n=2 可达 1.86-1.90× decode 加速。但真实高熵任务（前端动画/代码生成）上 MTP 投机需输出高度可预测才能靠 draft 命中省钱，而高熵任务 token 分布不可预测，draft 命中率低，验证每步多 pass 的开销超过省 token 的收益。

### 5.3 POC 加速 vs 真实长任务拖慢：机制对比分析（核心负责人补充，2026-08-30）

**问题**：为什么 POC 测试（08-29）中 MTP 单轮输出有加速（1.3-2.05×），但真实长任务（08-30 A/B）中 MTP n=1 反而拖慢约 52%？

#### 5.3.1 投机解码的加速机制

MTP 投机解码每个 step：
1. MTP 头（小头）draft n 个 token（便宜）
2. 主模型一次 forward 验证这 n 个 draft token（需对**完整上下文**做 attention）
3. 接受其中 k 个（0 ≤ k ≤ n），本 step 产出 (1+k) 个 token

加速比 ≈ (1 + k) / (1 + β)，其中：
- k = 平均每 step 接受的 draft token 数（= 接受率 × n），由**输出熵**决定
- β = 验证 forward 相对单次 decode 的额外开销，由**上下文长度**决定

**关键**：β 来自验证时"多出的 n 个位置对完整上下文做 attention"的成本。上下文越短，β≈0（验证几乎免费）；上下文越长，β 越大（每个 draft 位置都要对 L 个位置做 attention）。

#### 5.3.2 POC vs 真实长任务：四个维度的对照

| 维度 | POC（08-29） | 真实 A/B（08-30） | 对 MTP 的影响 |
|------|-------------|-------------------|--------------|
| 上下文长度 | 短（128-256 token） | 长（100K+，B10 在 131073 崩溃） | **主导因素**：POC β≈0（验证免费）；真实 β 大（验证昂贵） |
| 输出熵 | 低熵英文重复 91.2%；真实任务 50-90% | 持续高熵（代码+思考+多样内容） | 接受率 k：POC 高（0.5-0.9）；真实低 |
| 任务结构 | 单轮 burst（256 token 一次生成） | 多轮迭代 agent（读文件/思考/写码/执行/调整，数千 token） | 真实 decode 被 tool call 打断，内容多样 |
| 并发/批处理 | 单请求 | max_concurrency=2（连续批处理） | 真实验证开销挤占批处理算力 |

#### 5.3.3 为什么 POC 加速、真实拖慢（核心结论）

**POC 加速的原因**：
- 上下文短（128-256 token）→ 验证 forward 的额外 attention 成本极小（β≈0）
- 低熵输入（英文重复 91.2%；知识问答/翻译 80-88%）→ 接受率 k 高
- 单轮 256 token burst → 连续 decode，命中稳定
- 结果：加速比 (1+k)/(1+β) ≈ (1+k)/1 = 1+k > 1，POC 实测 1.3-2.05×

**真实长任务拖慢的原因**：
- 上下文长（100K+）→ 验证 forward 的额外 attention 成本巨大（β 大，每个 draft 位置都要对 100K 位置做 attention）
- 持续高熵（代码生成+思考 token）→ 接受率 k 低
- 多轮迭代 + 连续批处理 → 验证开销进一步放大
- 结果：加速比 (1+k)/(1+β) < 1（β > k），MTP 净拖慢约 52%

**一句话**：MTP 的验证成本随上下文长度增长，而接受率随输出熵升高而下降。POC 是"短上下文 + 低熵"（验证便宜 + 命中高）→ 加速；真实长任务是"长上下文 + 高熵"（验证昂贵 + 命中低）→ 两个不利因素叠加 → 拖慢。

#### 5.3.4 事实与推断的区分

**事实（有数据支撑）**：
- POC 低熵英文：91.2% 接受率，78-80 tok/s（MTP）vs 63-68（基线），~1.45-1.90×（见 `g56_mtp_smoke_record_20260829_v2.md` §4）
- POC 真实任务（256 token、短上下文）：n=1 1.3-1.7×、n=2 推理型 1.8-2.05×/创意型 1.3-1.4×（接受率 49-91%）（见 §5）
- POC 文档已明确指出：91.2% 是低熵英文最优场景，真实中文请求接受率显著更低；高熵文本 n=2 边际收益消失（见 §4.2、§5.1）
- 真实 A/B：MTP n=1，上下文至 131K（B10 在 131073>131072 崩溃），活跃 decode 中位数 A=45.1 vs B=21.8（B 慢 52%）

**推断（机制解释，未直接测量验证成本）**：
- 验证成本 β 随上下文长度增长（transformer attention 的已知性质，但本实验未直接测量 100K 上下文下的验证 forward 耗时）
- 真实 A/B 的接受率 k 低（由 52% 拖慢反推，未直接采集 /metrics spec 接受率）
- 连续批处理对 MTP 的额外拖累（推断，未单独做并发消融）

**可进一步验证的方向**：
- 在 100K 上下文下直接测量 MTP 验证 forward 的耗时（对比无 MTP 单步 decode）
- 采集真实 A/B 的 /metrics spec_decode 接受率（本实验未采集）
- 做上下文长度消融（1K/10K/50K/100K）看 MTP 加速比随上下文的变化曲线

### 5.4 建议

**建议全池回退无 MTP**（去掉 `--speculative-config`）：
1. 真实高熵/长上下文任务下 MTP 是负优化（decode 慢 17-26%）
2. MTP 侧任务完成度更差（崩溃 + 死循环）
3. 仅短上下文低熵场景 MTP 有收益，不抵整体拖累
